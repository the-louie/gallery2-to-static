# SEC-01: Fix Unsafe Numeric Entity Decoding in decodeHtmlEntities

**Date:** 2026-03-28
**Severity:** Critical | **OWASP:** CWE-79 (XSS)
**Affected files:**
- `backend/decodeHtmlEntities.ts` (lines 65-74)
- `frontend/src/utils/decodeHtmlEntities.ts` (lines 69-78)

---

## Problem Statement

`decodeHtmlEntities()` converts numeric HTML entities (`&#NNN;`, `&#xHHH;`, `&#NNN` without semicolon) to characters using `String.fromCharCode(parseInt(n, 10))` without validating the numeric value. This creates three distinct risks:

1. **Control character injection (codepoints 0-31, 127):** Null bytes (`&#0;`), backspace (`&#8;`), and other C0/C1 control characters can corrupt text rendering, break JSON serialization, or cause unexpected behavior in downstream consumers.

2. **Lone surrogate injection (codepoints 0xD800-0xDFFF):** `String.fromCharCode()` silently produces invalid lone surrogate characters. These can cause `JSON.stringify()` to produce malformed output, corrupt string comparisons, and crash some parsers.

3. **Overflow/truncation (codepoints > 0xFFFF):** `String.fromCharCode()` takes values modulo 65536, silently producing wrong characters. `&#120000;` (U+1D4C0, a math symbol) becomes `String.fromCharCode(120000 % 65536)` = `String.fromCharCode(54464)` = U+D4C0, a lone surrogate. This is both a correctness bug and a security concern.

### Data Flow Context

The function is called in two layers:
- **Backend** (`sqlUtils.ts`, `index.ts`): Decodes MySQL database values (titles, descriptions, summaries, ownerName, siteDescription) before writing to JSON files. Input source is Gallery 2 database content that was originally user-authored.
- **Frontend** (8+ component files, `bbcode.ts`): Re-decodes JSON data at render time as defensive decoding. Output goes to React DOM text nodes, aria-labels, alt attributes, and BBCode parser input.

React's DOM rendering escapes text content, so the primary risk is not direct XSS in the browser. The real risks are:
- Corrupted JSON output from backend (lone surrogates break `JSON.stringify`)
- Control characters in text that cause rendering artifacts or break string processing
- Incorrect character output from overflow (wrong characters displayed to users)

#### Task 1.1.3: Assess `String.fromCharCode` vs `String.fromCodePoint`
Confirm the behavioral difference:
- `String.fromCharCode(n)` — takes `n % 65536`. Safe for BMP (0-65535). Silently wrong for supplementary plane.
- `String.fromCodePoint(n)` — handles full Unicode (0-0x10FFFF). Throws `RangeError` for invalid values. Available since ES2015 (well within project's ES2020 target).

Decision: Replace `fromCharCode` with `fromCodePoint` for correctness, and add explicit range validation for security.

### Section 1.2: Define Allowed Codepoint Ranges

#### Task 1.2.1: Define the validation rules
The validation function should reject:

| Range | Reason |
|-------|--------|
| < 9 (0x00-0x08) | C0 control characters (null, SOH through BS) |
| 11-12 (0x0B-0x0C) | VT, FF (uncommon controls) |
| 14-31 (0x0E-0x1F) | SO through US (control characters) |
| 127 (0x7F) | DEL control character |
| 128-159 (0x80-0x9F) | C1 control characters |
| 0xD800-0xDFFF | Surrogate pair range (invalid in isolation) |
| 0xFDD0-0xFDEF | Unicode noncharacters |
| 0xFFFE-0xFFFF | Unicode noncharacters |
| > 0x10FFFF | Beyond Unicode range |

Allow:
| Range | Reason |
|-------|--------|
| 9 (0x09) | Tab — common in text |
| 10 (0x0A) | Line feed — common in text |
| 13 (0x0D) | Carriage return — common in text |
| 32-126 (0x20-0x7E) | Printable ASCII |
| 160-0xD7FF (0xA0-0xD7FF) | BMP printable characters (Latin, Nordic, CJK, etc.) |
| 0xE000-0xFDCF | BMP printable (Private Use + more) |
| 0xFDF0-0xFFFD | BMP printable (remaining) |
| 0x10000-0x1FFFD, etc. | Supplementary planes (emoji, historic scripts, etc.), excluding per-plane noncharacters |

Simplified approach: reject control chars, surrogates, and out-of-range. Allow everything else. This covers the real security risks without being overly restrictive.

#### Task 1.2.2: Decide replacement behavior for rejected codepoints
When a codepoint is rejected, the replacement should return the **original entity text unchanged** (e.g., `&#0;` stays as `&#0;`). This is the safest approach because:
- It preserves the original string (no data loss)
- It's visible if anyone inspects the output (not silently swallowed)
- It matches browser behavior for unrecognized entities
- It doesn't introduce new characters

## Phase 2: Implementation

### Section 2.1: Create the Validation Helper

#### Task 2.1.1: Add `safeFromCodePoint()` helper function
Add a private helper function in both `decodeHtmlEntities.ts` files. This function:
1. Parses the numeric value
2. Validates it's within allowed ranges
3. Returns the character via `String.fromCodePoint()`, or the original entity text if invalid

```typescript
/**
 * Convert a numeric codepoint to a character if it falls within safe Unicode
 * ranges. Returns the original entity text unchanged for control characters,
 * lone surrogates, noncharacters, and out-of-range values.
 */
function safeFromCodePoint(codepoint: number, original: string): string {
  if (
    !Number.isFinite(codepoint) ||
    codepoint < 0 ||
    codepoint > 0x10ffff ||
    // C0 controls (except tab, LF, CR)
    (codepoint <= 0x08) ||
    (codepoint >= 0x0b && codepoint <= 0x0c) ||
    (codepoint >= 0x0e && codepoint <= 0x1f) ||
    // DEL + C1 controls
    (codepoint >= 0x7f && codepoint <= 0x9f) ||
    // Surrogate pairs (invalid in isolation)
    (codepoint >= 0xd800 && codepoint <= 0xdfff) ||
    // Unicode noncharacters
    (codepoint >= 0xfdd0 && codepoint <= 0xfdef) ||
    (codepoint & 0xfffe) === 0xfffe // catches U+FFFE/U+FFFF, U+1FFFE/U+1FFFF, etc.
  ) {
    return original;
  }
  return String.fromCodePoint(codepoint);
}
```

Location: Place immediately above the `decodeHtmlEntities()` export in each file. Do not export it — it's an internal helper.
