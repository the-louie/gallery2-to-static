# SEC-04: Fix Path Traversal in imageUrl.ts via pathComponent

**Date:** 2026-03-28
**Severity:** High | **OWASP:** CWE-22 (Path Traversal)
**Affected files:**
- `frontend/src/utils/imageUrl.ts` (lines 29-31, and all URL construction functions)

---

## Problem Statement

`ensureNoLeadingSlash()` only strips leading slashes from path segments before concatenation with base URLs. It does not validate that the path contains no `..` segments. If a `pathComponent`, `urlPath`, `thumbnailUrlPath`, `highlightThumbnailUrlPath`, or `highlightImageUrl` value contains directory traversal sequences, the constructed URL escapes the intended `/g2data/albums/` or `/g2data/thumbnails/` directory scope.

For example:
- Input: `../../etc/passwd`
- After `ensureNoLeadingSlash()`: `../../etc/passwd` (unchanged, no leading slash)
- Constructed URL: `/g2data/albums/../../etc/passwd`
- Browser resolves to: `/etc/passwd`

### Attack Vectors

The path values originate from pre-generated JSON files produced by the backend extraction script. The primary risk scenarios are:

1. **Compromised JSON data:** If an attacker modifies the static JSON files served by the web server (e.g., via a separate file upload vulnerability or supply chain attack), they can inject traversal paths that cause the frontend to fetch arbitrary server resources.

2. **Malicious Gallery 2 database content:** If the Gallery 2 database contains crafted pathComponent values (from a compromised admin or SQL injection in the original Gallery 2 instance), those values flow through the backend extraction into JSON files without traversal validation.

3. **CSS injection via `getAlbumHighlightImageUrl`:** In `RootAlbumListBlock.tsx:87`, the highlight image URL is interpolated into a CSS `url()` value: `url("${highlightImageUrl.replace(/"/g, '\\"')}")`. A traversal path could reference an attacker-controlled resource.

### Data Flow

All affected paths flow through the same bottleneck:

```
JSON data (pathComponent, urlPath, thumbnailUrlPath, etc.)
       |
       v
  ensureNoLeadingSlash()  <-- only strips leading slashes, no traversal check
       |
       v
  String concatenation: `${baseUrl}/${sanitizedPath}`
       |
       v
  Used as: <img src=...>, fetch() URL, CSS url() background-image
```

### Callers of Exported Functions

| Function | Callers | Path fields used |
|----------|---------|-----------------|
| `getImageUrl()` | `useProgressiveImage.ts:108-109`, `useImagePreload.ts:51` | `image.urlPath ?? image.pathComponent` |
| `getImageUrlWithFormat()` | (test-only usage currently) | `image.urlPath ?? image.pathComponent` |
| `getAlbumThumbnailUrl()` | `AlbumCard.tsx:53`, `RootAlbumListBlock.tsx:84` | `album.thumbnailUrlPath`, `album.highlightThumbnailUrlPath`, `album.thumbnailPathComponent`, `album.highlightImageUrl` |
| `getAlbumHighlightImageUrl()` | `RootAlbumListBlock.tsx:83` | `album.highlightImageUrl` |

All callers pass these URLs to either `<img src>` attributes, `fetch()` calls via `fetchImageAsObjectUrl()`, or CSS `url()` values. None perform their own traversal validation.

- `useImagePreload.ts`: URLs passed to `preloadImage()` which creates `new Image()` and sets `.src` -- a network request.

#### Task 1.1.4: Assess whether URL-encoded traversal is a risk
Check whether `%2e%2e%2f` (URL-encoded `../`) could bypass a literal `..` check. Since the path values come from JSON (not from URL parameters), they are plain strings, not URL-encoded. The browser's URL resolver handles the traversal on the plain `..` segments. URL-encoded variants (`%2e%2e`) in a path are not automatically decoded by the browser before path resolution, so they would result in a literal `%2e%2e` directory name (which doesn't exist), not traversal.

Decision: Checking for literal `..` path segments is sufficient. URL-encoded variants are not a practical concern for JSON-sourced paths.

### Section 1.2: Define Sanitization Strategy

#### Task 1.2.1: Choose between throw vs return-safe-fallback
Two options for handling traversal paths:

**Option A: Throw an error**
- `if (path.includes('..')) throw new Error('Path traversal detected');`
- Pro: Fail-fast, obvious signal to developers.
- Con: Callers must handle exceptions. Unhandled error crashes the component (caught by ErrorBoundary, but disruptive to the user).

**Option B: Return base URL (empty path fallback)**
- `if (containsPathTraversal(path)) return baseUrl;`
- Pro: Graceful degradation -- image simply doesn't load (broken image icon), same behavior as a missing image. No component crash.
- Con: Silent failure; harder to notice during development.

Decision: **Option B with a `console.warn`**. This matches the existing pattern in the file where `null`/empty pathComponent returns the base URL (lines 54-56, 133-135). A warning logged to the console aids debugging without disrupting the user experience. This is consistent with the backend pattern documented in CLAUDE.md: "console.warn for non-critical issues."

#### Task 1.2.2: Define the validation function signature
Create a new private helper function:

```typescript
/**
 * Check whether a path contains directory traversal sequences.
 * Returns true if the path contains ".." as a path segment (e.g., "../", "foo/../bar").
 */
function containsPathTraversal(path: string): boolean
```

The check must detect `..` as a path segment, not as a substring of filenames. For example:
- `../../etc/passwd` -- traversal (reject)
- `foo/../bar/photo.jpg` -- traversal (reject)
- `../photo.jpg` -- traversal (reject)
- `photo..jpg` -- NOT traversal (allow, `..` is part of filename)
- `album.../photo.jpg` -- NOT traversal (allow, `...` is part of directory name)

Approach: Split the path on `/` and check if any segment is exactly `..`. This is more precise than `path.includes('..')` which would incorrectly reject `photo..jpg`.

Refined implementation:
```typescript
function containsPathTraversal(path: string): boolean {
  return path.split('/').some((segment) => segment === '..');
}
```

This handles all traversal variants:
- `../../etc/passwd` splits to `['..', '..', 'etc', 'passwd']` -- segment `..` found
- `foo/../bar` splits to `['foo', '..', 'bar']` -- segment `..` found
- `photo..jpg` splits to `['photo..jpg']` -- no segment equals `..`
- `album.../photo.jpg` splits to `['album...', 'photo.jpg']` -- no segment equals `..`

#### Task 1.2.3: Decide where to apply the check
Two options:

**Option A: Inside `ensureNoLeadingSlash()`**
- Rename to `sanitizePath()` that does both leading-slash removal and traversal check.
- Pro: Single function handles all path sanitization. Every existing call site is automatically protected.
- Con: Mixes concerns (slash normalization + security validation). The function name implies a simple string operation but now has security side effects.

**Option B: New `sanitizePath()` wrapper that calls `ensureNoLeadingSlash()` then validates**
- Pro: Clear separation of concerns. Each function has a single responsibility.
- Con: Must replace every `ensureNoLeadingSlash()` call with `sanitizePath()`.

**Option C: Add traversal check at the top of each exported function**
- Pro: Validation at the boundary, close to the public API.
- Con: Repetitive; easy to miss when adding new functions.

Decision: **Option A (modified)**. Rename `ensureNoLeadingSlash()` to `sanitizePath()`. The new function strips leading slashes AND rejects traversal paths. Since `ensureNoLeadingSlash` is a private function (not exported) called from exactly 6 locations within the same file, renaming it is safe and ensures complete coverage with no risk of missing a call site. The JSDoc will clearly document both behaviors.

## Phase 2: Implementation

### Section 2.1: Add Path Traversal Detection Helper

#### Task 2.1.1: Add `containsPathTraversal()` helper function
Add a private helper function in `frontend/src/utils/imageUrl.ts`, placed above the existing `ensureNoLeadingSlash()` function.

```typescript
/**
 * Check whether a path contains directory traversal sequences.
 * Returns true if any segment of the path (split on '/') is exactly '..'.
 * Does not flag '..' appearing within filenames (e.g. 'photo..jpg').
 */
function containsPathTraversal(path: string): boolean {
  return path.split('/').some((segment) => segment === '..');
}
```

Location: Place immediately above the `ensureNoLeadingSlash` function. Do not export it -- it's an internal helper.

### Section 2.2: Replace `ensureNoLeadingSlash` with `sanitizePath`

#### Task 2.2.1: Rename and extend `ensureNoLeadingSlash()`
Replace the existing `ensureNoLeadingSlash` function with `sanitizePath`. The new function:
1. Checks for path traversal and returns empty string (triggering base-URL-only return) with a console.warn if found
2. Strips leading slashes (existing behavior)

Before:
```typescript
/**
 * Strip leading slashes from a path segment so concatenation with baseUrl (no trailing slash) never produces double slashes.
 */
function ensureNoLeadingSlash(path: string): string {
  return path.replace(/^\/+/, '');
}
```

After:
```typescript
/**
 * Sanitize a URL path segment: reject directory traversal and strip leading slashes.
 *
 * Returns the cleaned path for safe concatenation with a base URL. If the path
 * contains '..' traversal segments, logs a warning and returns an empty string
 * so the caller falls back to the base URL alone.
 */
function sanitizePath(path: string): string {
  if (containsPathTraversal(path)) {
    console.warn(
      `[imageUrl] Path traversal detected and blocked: "${path.length > 80 ? path.slice(0, 80) + '...' : path}"`,
    );
    return '';
  }
  return path.replace(/^\/+/, '');
}
```

Note: The warn message truncates long paths to 80 characters to avoid log flooding with very long crafted paths.

#### Task 2.2.2: Update all call sites from `ensureNoLeadingSlash` to `sanitizePath`
Replace all 6 occurrences of `ensureNoLeadingSlash(` with `sanitizePath(` in the same file:

1. Line 58 in `constructThumbnailUrl()`:
   `const path = sanitizePath(pathComponent);`

2. Line 137 in `constructFullImageUrl()`:
   `const pathWithFormat = replaceExtension(sanitizePath(pathComponent), format);`

3. Line 271 in `getAlbumThumbnailUrl()`:

4. Line 275 in `getAlbumThumbnailUrl()`:

5. Line 286 in `getAlbumThumbnailUrl()`:

6. Line 309 in `getAlbumHighlightImageUrl()`:

#### Task 2.2.3: Verify empty-string handling in callers
When `sanitizePath()` returns `''` (traversal detected), the resulting URL is `${baseUrl}/` (base URL with trailing slash). Verify this is acceptable:

- `constructThumbnailUrl()`: Line 58 sets `path = ''`. Then `lastSlashIndex === -1`, so `directory = ''`, `filename = ''`. The constructed URL becomes `${baseUrl}/t__` (thumb prefix + empty filename). This is a non-existent resource, which will 404 gracefully.
- `constructFullImageUrl()`: Line 137, `replaceExtension('', format)` returns `''` or `'.webp'` etc. URL becomes `${baseUrl}/` or `${baseUrl}/.webp`. Non-existent, 404s gracefully.
- Direct concatenations in `getAlbumThumbnailUrl()` and `getAlbumHighlightImageUrl()`: URL becomes `${baseUrl}/`. Non-existent, 404s gracefully.

All cases produce URLs that will fail to load (broken image icon) rather than traversing outside the intended directory. This matches the existing behavior for empty/null pathComponent values.
