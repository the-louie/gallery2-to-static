# SEC-11: Add Path Component Validation in pathResolution.ts

**Date:** 2026-03-28
**Severity:** Medium | **OWASP:** CWE-22 (Path Traversal)
**Affected files:**
- `backend/pathResolution.ts` (lines 10-24)
- `backend/pathResolution.test.ts`

---

## Problem Statement

`buildPathsFromPathComponent()` in `backend/pathResolution.ts` takes a `pathComponentChain` array (sourced from the Gallery 2 database `FileSystemEntity.pathComponent` column) and joins the elements into a relative file path using `/` as separator. The function performs no validation on individual path components before joining.

If a database record contains a malicious `pathComponent` value such as `..`, `../`, `../../etc/passwd`, or a component containing `/` or `\` characters, the resulting joined path could escape the intended `g2data/albums/` directory tree. A null byte (`\0`) in a component could truncate paths in some environments.

### Current Code (lines 10-24)

```typescript
export function buildPathsFromPathComponent(
    pathComponentChain: string[],
    thumbPrefix: string,
): { urlPath: string; thumbnailUrlPath: string } {
    if (!pathComponentChain.length) {
        return { urlPath: '', thumbnailUrlPath: '' };
    }
    const relativePath = pathComponentChain.filter(Boolean).join('/').replace(/^\/+/, '');
    const lastSlash = relativePath.lastIndexOf('/');
    const dir = lastSlash === -1 ? '' : relativePath.slice(0, lastSlash);
    const filename = lastSlash === -1 ? relativePath : relativePath.slice(lastSlash + 1);
    const thumbFilename = thumbPrefix + filename;
    const thumbnailUrlPath = dir ? `${dir}/${thumbFilename}` : thumbFilename;
    return { urlPath: relativePath, thumbnailUrlPath };
}
```

The `.filter(Boolean)` call filters out empty strings, and `.replace(/^\/+/, '')` strips leading slashes, but neither addresses `..` sequences, embedded `/` or `\` characters, or null bytes within individual components.

### Data Flow Context

The function is called in three places within `backend/index.ts`:

1. **Line 218** (`buildHighlightPathsFromResult`): Constructs highlight image paths from `FirstPhotoResult.pathComponent` chain + `photo.pathComponent`. Result written to album JSON as `highlightImageUrl` and `highlightThumbnailUrlPath`.

2. **Line 344** (photo processing): Constructs `urlPath` and `highlightThumbnailUrlPath` for `GalleryPhotoItem` children. The `urlPath` is also used to build `sourcePath` and `destPath` for thumbnail generation via `path.join(albumsRoot, fullPath)` (line 349) and `path.join(thumbnailsRoot, highlightThumbnailUrlPath)` (line 350).

3. **Line 454** (album highlight thumbnail): Constructs `thumbnailUrlPath` for album children's highlight thumbnails. Written to album JSON output.

All `pathComponent` values originate from the Gallery 2 MySQL database (`FileSystemEntity` table, `pathComponent` column), read via parameterized SQL in `sqlUtils.ts:20`. The database is a trusted local source in normal operation, but defense-in-depth requires validation since:
- The backend generates file paths used with `path.join()` and `fs` operations (thumbnail generation)
- The output JSON is consumed by the frontend which constructs image URLs from these paths
- A compromised or tampered database could inject traversal sequences

### Risk Assessment

Since this is a backend-only, one-shot admin tool run locally (not internet-facing), the practical attack surface is limited to a compromised MySQL database. However, the fix is straightforward and prevents path traversal in the generated JSON and thumbnail file operations. The downstream consumers (frontend image URL construction, `generateThumbnail.ts` file I/O) both benefit from validated paths at the source.

### Section 1.1: Understand Current Behavior

#### Task 1.1.1: Verify current function behavior with traversal inputs

- Input `['..', '..', 'etc', 'passwd']`:

- Input `['album', '../../../etc/passwd']`:
  - `.join('/')` produces `album/../../../etc/passwd`

- Input `['album/../../etc/passwd']`:
  - Single component with embedded `/`
  - `.join('/')` produces `album/../../etc/passwd`
  - `relativePath` = `album/../../etc/passwd` -- traversal achieved

- Input `['album', 'photo\0.jpg']`:
  - `.join('/')` produces `album/photo\0.jpg`
  - Null byte could truncate path in some file system APIs

Verify the three call sites in `backend/index.ts` (lines 218, 344, 454) and confirm that all `pathComponent` values originate from the database via `sqlUtils.ts:20` (`fse.pathComponent as pathComponent`).

Confirm that the `pathComponent` parameter in `main()` (line 259) starts as an empty array at the top-level call and accumulates album `pathComponent` values from database results as recursion deepens.

#### Task 1.1.3: Assess downstream impact of generated paths
Trace how the output `urlPath` and `thumbnailUrlPath` are used:

- **Thumbnail generation** (line 349-350): `path.join(albumsRoot, fullPath)` and `path.join(thumbnailsRoot, highlightThumbnailUrlPath)` -- a traversal path here could read/write arbitrary files.
- **JSON output**: Written to `data/{albumId}.json` as `urlPath`, `thumbnailUrlPath`, `highlightThumbnailUrlPath` fields. Frontend constructs URLs like `/g2data/albums/${urlPath}` -- traversal could serve unintended files.

### Section 1.2: Define Validation Rules

#### Task 1.2.1: Define the set of prohibited patterns
Each individual path component (before joining) must be validated. A component is invalid if it:

| Pattern | Reason |
|---------|--------|
| Contains `..` | Directory traversal (covers `..`, `../`, `a/../b`) |
| Contains `/` | Path separator injection (bypasses per-component validation) |
| Contains `\` | Windows path separator (defense-in-depth, prevents `..\\`) |
| Contains null byte `\0` | Path truncation in some environments |

Note: The `..` check uses `includes('..')` which catches `..` anywhere in the component. This is intentionally broad -- legitimate Gallery 2 path components are filenames and directory names, never containing `..` as a substring. A filename like `file..ext` is theoretically possible but extremely unlikely in Gallery 2 data, and the security benefit outweighs the negligible false-positive risk.

#### Task 1.2.2: Decide rejection behavior
When an invalid component is detected, the function should:
1. Log a warning via `console.warn` (consistent with the backend pattern of warning on non-critical issues during extraction, per CLAUDE.md)
2. Return empty paths `{ urlPath: '', thumbnailUrlPath: '' }` (same as the empty-chain case)

Rationale for returning empty paths rather than throwing:
- The backend processes many items in a batch; throwing would abort the entire extraction
- An empty path causes the item to have no image URL, which is a safe degradation (image simply won't display)
- The `console.warn` ensures the admin sees the problematic component
- This matches the existing pattern: line 14-16 already returns empty paths for the empty-chain edge case

## Phase 2: Implementation

### Section 2.1: Add the Validation Helper

#### Task 2.1.1: Create `isValidPathComponent()` helper function
Add a private helper function in `backend/pathResolution.ts`, placed above the `buildPathsFromPathComponent` export. Do not export it -- it is an internal helper.

```typescript
/**
 * Validate a single path component for unsafe sequences.
 * Rejects components containing '..', '/', '\', or null bytes.
 */
function isValidPathComponent(component: string): boolean {
  return (
    !component.includes('..') &&
    !component.includes('/') &&
    !component.includes('\\') &&
    !component.includes('\0')
  );
}
```

Design notes:
- Pure function with no side effects (validation only)
- Uses `String.prototype.includes()` for clarity and correctness
- Checks for `..` as a substring rather than exact match to catch `a../b` patterns
- Does not check for empty strings -- those are already handled by `.filter(Boolean)` in the main function

### Section 2.2: Integrate Validation into buildPathsFromPathComponent

#### Task 2.2.1: Add validation loop before path joining
Insert validation between the empty-chain check (line 14-16) and the path joining (line 17). Iterate over each non-empty component and check with `isValidPathComponent()`.

The function after modification:

```typescript
export function buildPathsFromPathComponent(
    pathComponentChain: string[],
    thumbPrefix: string,
): { urlPath: string; thumbnailUrlPath: string } {
    if (!pathComponentChain.length) {
        return { urlPath: '', thumbnailUrlPath: '' };
    }
    const components = pathComponentChain.filter(Boolean);
    for (const component of components) {
        if (!isValidPathComponent(component)) {
            console.warn(
                `Invalid path component rejected: ${JSON.stringify(component)}`,
            );
            return { urlPath: '', thumbnailUrlPath: '' };
        }
    }
    const relativePath = components.join('/').replace(/^\/+/, '');
    const lastSlash = relativePath.lastIndexOf('/');
    const dir = lastSlash === -1 ? '' : relativePath.slice(0, lastSlash);
    const filename = lastSlash === -1 ? relativePath : relativePath.slice(lastSlash + 1);
    const thumbFilename = thumbPrefix + filename;
    const thumbnailUrlPath = dir ? `${dir}/${thumbFilename}` : thumbFilename;
    return { urlPath: relativePath, thumbnailUrlPath };
}
```

Key changes:
- Extract `components = pathComponentChain.filter(Boolean)` to a named variable (used in both validation loop and join)
- Add `for...of` loop calling `isValidPathComponent()` on each component
- On invalid component: warn and return empty paths (safe degradation)
- Reuse the `components` variable in the existing `.join('/')` call (replaces the previous inline `.filter(Boolean)`)

#### Task 2.2.2: Verify the edit preserves existing behavior
The refactoring must not change behavior for valid inputs:
- Empty chain: still returns empty paths (unchanged early return)
- Components with empty strings: still filtered by `.filter(Boolean)` (now extracted to variable)
- Valid components: pass `isValidPathComponent()`, then proceed to the same join/split logic
- Leading slash stripping: unchanged `.replace(/^\/+/, '')`

## Phase 4: Code Review

### Section 4.1: Verify Implementation Correctness

#### Task 4.1.1: Confirm validation covers all attack vectors
Walk through each prohibited pattern mentally:

- `['..']` -- `'..'` contains `..` -- caught by `includes('..')` check
- `['a/..']` -- `'a/..'` contains `..` -- caught by `includes('..')` check. Also caught by `includes('/')` check
- `['a', '..', 'b']` -- `'..'` contains `..` -- caught
- `['a\0b']` -- `'a\0b'` contains `\0` -- caught by `includes('\0')` check
- `['a\\b']` -- `'a\\b'` contains `\\` -- caught by `includes('\\')` check
- `['a/b']` -- `'a/b'` contains `/` -- caught by `includes('/')` check

#### Task 4.1.2: Confirm no false positives for legitimate Gallery 2 paths
Verify that common Gallery 2 path component patterns pass validation:

- `'DSC00800.jpg'` -- dots are single, no prohibited patterns -- passes
- `'BAK.dhw05'` -- single dots in album name -- passes
- `'CV-LAN'` -- hyphen, uppercase -- passes
- `'Sommarstugan'` -- Nordic characters (if present) -- passes
- `'.hidden'` -- single dot prefix (unix hidden file) -- passes (no `..`)
- `'file..ext'` -- double dot in filename -- **rejected** (contains `..`). This is the only theoretical false positive. Gallery 2 does not generate such pathComponents, and the security benefit justifies this strictness.

#### Task 4.1.3: Verify no dead code or unnecessary changes
Confirm:
- No unused imports added
- No commented-out code left behind
- The `isValidPathComponent` helper is used only by `buildPathsFromPathComponent`

#### Task 4.1.4: Verify the console.warn message is informative

- Identify the function context (path component validation)

### Section 4.2: Integration Verification

#### Task 4.2.1: Downstream impact of empty-path return
When validation fails and empty paths are returned:

- **Thumbnail generation** (index.ts:349-350): `path.join(albumsRoot, '')` produces just `albumsRoot`. The `generateThumbnail` function would attempt to read a directory as an image, which would fail with a `'missing'` or `'invalid'` status and be logged. No file escape.
- **JSON output**: `urlPath: ''` and `thumbnailUrlPath: ''` in the output JSON. Frontend constructs `/g2data/albums/` (no file path), which returns a 404. Safe degradation.
- **Highlight image**: Empty `highlightImageUrl` and `highlightThumbnailUrlPath` cause the album to show no highlight image. Acceptable for a corrupted database entry.

#### Task 4.2.2: Confirm no frontend changes required
The validation is entirely in the backend extraction script. The frontend receives pre-validated paths in JSON. No frontend code changes are needed.

#### Task 4.2.3: Confirm the `thumbPrefix` parameter is not a vector
The `thumbPrefix` parameter (e.g., `'t__'`) is hardcoded in the backend configuration, not sourced from the database. It does not need validation in this fix.
