# SEC-07: Fix ReDoS Vulnerability in Search Regex with Lazy Quantifiers

**Date:** 2026-03-28
**Severity:** High | **OWASP:** CWE-1333 (ReDoS)
**Affected files:**
- `frontend/src/utils/searchUtils.ts` (lines 36-38, 76-80)

---

## Problem Statement

`matchSubsequence()` converts a user-supplied query string into a regex pattern by joining each character with `.*?` (lazy quantifier). For example, the query `"fbsd"` becomes the regex `f.*?b.*?s.*?d`. When the regex engine attempts to match this pattern against a long text and the match **fails**, the engine must explore an exponential number of backtracking paths through all the `.*?` alternatives before concluding there is no match.

### Why This Is Exploitable

The vulnerability is triggered specifically on **non-matching** inputs where the characters appear partially but not fully in order. For a query of length `n` against text of length `m`, the worst-case backtracking complexity is approximately `O(m^n)`. A crafted query of 20+ characters against a text of 500+ characters can cause the browser regex engine to hang for seconds or longer, freezing the UI thread.

### Attack Vector

The query string comes directly from user input via the `SearchBar` component:
1. User types into the search input (`SearchBar.tsx:238-248`)
2. After debounce (300ms), the query is passed to `useSearch` hook (`useSearch.ts:128`)
3. `SearchIndex.search()` calls `matchSubsequence(item.title, query)` and `matchSubsequence(item.description, query)` for **every item in the search index** (`searchIndex.ts:152-155`)
4. `highlightText()` and `highlightTextAsHtml()` in `searchHighlight.ts` also call `matchSubsequence()` for rendering results

A single malicious query triggers `matchSubsequence()` hundreds or thousands of times (once per search index item, plus again per result for highlighting), amplifying the per-call cost.

### Data Flow

```
User input (SearchBar)
       |
       v
useSearch hook (useSearch.ts:128)
       |
       v
SearchIndex.search() (searchIndex.ts:144)
       |
       v  (called for EACH index item)
matchSubsequence(item.title, query)    -- searchIndex.ts:152
matchSubsequence(item.description, query) -- searchIndex.ts:154
       |
       v  (called again for EACH result, for display)
highlightText(text, query)             -- searchHighlight.ts:68
highlightTextAsHtml(text, query)       -- searchHighlight.ts:124
```

### Current Guards (Insufficient)

The function already has two early returns (lines 60-72):
- Empty text/query: returns `{ matched: false }` -- good but unrelated to ReDoS
- Query longer than text: returns `{ matched: false }` -- prevents some cases but not the core issue

These do not protect against a 30-character query matched against a 200-character text where backtracking is catastrophic.

## Phase 1: Research & Impact Analysis

### Section 1.1: Understand Current Behavior

#### Task 1.1.1: Verify the regex construction pattern
Read `frontend/src/utils/searchUtils.ts:74-80` and confirm the regex is built as:
```typescript
const escapedChars = trimmedQuery.split('').map(char => escapeRegex(char)).join('.*?');
const regexPattern = new RegExp(escapedChars, 'i');
```
Each query character is escaped (safe against regex injection) and joined with `.*?`. For a query of `n` characters, this creates `n-1` lazy quantifiers. The `'i'` flag enables case-insensitive matching, which adds additional per-character overhead.

#### Task 1.1.2: Confirm backtracking behavior with worst-case inputs
Understand the worst case: query `"abcdefghij"` against text `"axxxxxxxxbxxxxxxxxcxxxxxxxxdxxxxxxxxexxxxxxxxfxxxxxxxxgxxxxxxxxhxxxxxxxxixxxxxxxxz"` (characters a-i present but j absent). The regex engine must:
1. Match `a` at position 0
2. For each subsequent character, try every possible position for `.*?`
3. When `j` fails to match at the end, backtrack through all combinations of positions for a-i
4. This creates exponential path exploration

A query of 15+ characters with partial matches can cause multi-second hangs. With 20+ characters, the browser tab may become unresponsive.

#### Task 1.1.3: Identify all callers and their input constraints
Verify the caller inventory:

**Direct callers of `matchSubsequence()`:**
- `searchIndex.ts:152` -- `matchSubsequence(item.title, query)` where `item.title` comes from pre-built search index JSON (album titles, typically 5-100 chars)
- `searchIndex.ts:154` -- `matchSubsequence(item.description, query)` where `item.description` comes from pre-built search index JSON (album descriptions, typically 0-500 chars)
- `searchHighlight.ts:68` -- `highlightText(text, query)` where text is a search result title/description being rendered
- `searchHighlight.ts:124` -- `highlightTextAsHtml(text, query)` where text is a search result title/description being rendered as HTML

**Query source:**
- `SearchBar.tsx:238-248` -- HTML `<input type="search">` element, no `maxLength` attribute, user can type or paste arbitrarily long strings
- Query flows through URL: `performSearch()` encodes to `?q=...` URL parameter (`SearchBar.tsx:111`)
- `SearchResultsPage` reads `q` from URL params and passes to `useSearch`

**Text sources (from search index):**
- Album titles: typically short (5-100 characters), sourced from Gallery 2 database
- Album descriptions: can be longer (0-500+ characters), also from database
- Both are pre-decoded clean text (HTML entities already resolved by backend)

#### Task 1.1.4: Assess amplification factor
The search index may contain hundreds to thousands of items. Each `search()` call invokes `matchSubsequence()` twice per item (title + description). A gallery with 500 albums means 1000 regex executions per search query. If each takes 100ms due to backtracking, total time is 100 seconds -- complete UI freeze.

### Section 1.2: Define Input Length Limits

#### Task 1.2.1: Choose appropriate limits
Two guards are needed:

| Guard | Limit | Rationale |
|-------|-------|-----------|
| Query length | > 50 characters | No realistic album search query exceeds 50 chars. Typical queries are 2-20 chars. A 50-char query creates 49 lazy quantifiers, which is already borderline. |
| Combined query + text length | > 2000 characters | Limits the total search space. With a 50-char query against a 1950-char text, backtracking is bounded. Typical album titles are <100 chars, descriptions <500 chars, so this limit is generous. |

These limits match the fix specified in the SEC-07 description, adjusted from the original 1000 combined limit to 2000 to accommodate longer album descriptions without rejecting legitimate searches. The existing tests (lines 84-123) already use 2000 as the combined limit threshold, confirming this is the intended value.

#### Task 1.2.2: Decide return behavior for rejected inputs
When input exceeds limits, return `{ matched: false, matchIndices: [] }`. This is consistent with other early returns in the function (empty text, empty query, query longer than text). The search simply shows no results for that item, which is the correct UX for an absurdly long query.

#### Task 1.2.3: Decide where to place the guards
Add the length checks **after** the existing early returns (after line 72, before the regex construction at line 74). This keeps the validation logic grouped together and ensures the checks run before any regex is compiled or executed. The order should be:
1. Empty text check (existing, line 61)
2. Empty/whitespace query check (existing, line 65)
3. Query longer than text check (existing, line 70)
4. **NEW: Query length > 50 check**
5. **NEW: Combined length > 2000 check**
6. Regex construction and execution (existing, line 76+)

## Phase 2: Implementation

### Section 2.1: Add Input Length Validation Guards

#### Task 2.1.1: Add length constants at module level
Add descriptive constants at the top of `frontend/src/utils/searchUtils.ts`, after the `SubsequenceMatch` interface (after line 28) and before the `escapeRegex` function:

```typescript
/**
 * Maximum allowed query length for subsequence matching.
 * Queries longer than this are rejected to prevent ReDoS from
 * exponential backtracking in the lazy quantifier regex pattern.
 */
const MAX_QUERY_LENGTH = 50;

/**
 * Maximum allowed combined length of query + text for subsequence matching.
 * Limits the total search space to prevent catastrophic backtracking
 * when long queries are matched against long text.
 */
const MAX_COMBINED_LENGTH = 2000;
```

#### Task 2.1.2: Add query length guard to `matchSubsequence()`
After the existing `trimmedQuery.length > text.length` check (line 70-72), add:

```typescript
// SEC-07: Reject queries exceeding maximum length to prevent ReDoS
// The .*? lazy quantifier pattern creates exponential backtracking risk
// proportional to query length
if (trimmedQuery.length > MAX_QUERY_LENGTH) {
  return { matched: false, matchIndices: [] };
}
```

#### Task 2.1.3: Add combined length guard to `matchSubsequence()`
Immediately after the query length guard, add:

```typescript
// SEC-07: Reject when combined input size exceeds safe threshold
if (trimmedQuery.length + text.length > MAX_COMBINED_LENGTH) {
  return { matched: false, matchIndices: [] };
}
```

### Section 2.2: Verify No Other Changes Needed

#### Task 2.2.1: Confirm `calculateSubsequenceScore()` needs no changes
`calculateSubsequenceScore()` does not construct or execute any regex. It only performs arithmetic on the `matchIndices` array. No ReDoS risk exists in this function. No changes needed.

#### Task 2.2.2: Confirm `escapeRegex()` needs no changes
`escapeRegex()` uses a single-pass fixed regex (`/[.*+?^${}()|[\]\\]/g`) that cannot backtrack catastrophically regardless of input. No changes needed.

#### Task 2.2.3: Confirm caller functions need no changes
The callers (`searchIndex.ts`, `searchHighlight.ts`) pass through to `matchSubsequence()` and handle the `{ matched: false }` return correctly:
- `searchIndex.ts:152-155` -- checks `titleMatch.matched` and `descriptionMatch.matched`, skips item if both false
- `searchHighlight.ts:69-71` -- checks `match.matched`, returns unhighlighted text if false
- `searchHighlight.ts:125-127` -- same pattern

No caller changes are needed. The guards in `matchSubsequence()` are sufficient.

### Section 4.3: Security Assessment

#### Task 4.3.1: Confirm the fix addresses the stated vulnerability
The SEC-07 description states: "Pattern `char1.*?char2.*?char3` is vulnerable to catastrophic backtracking on non-matching long input."

The fix prevents this by:
1. Limiting query length to 50 characters, which caps the number of `.*?` quantifiers at 49
2. Limiting combined text+query length to 2000, which bounds the search space

With these limits, the worst-case backtracking for a 50-char query against a 1950-char text is bounded, preventing the browser regex engine from hanging.

#### Task 4.3.2: Assess residual risk
Even with the guards, a 50-character query against a 1950-character non-matching text could still cause measurable (but bounded) backtracking. However:
- The search index items (album titles/descriptions) are typically much shorter than 1950 chars
- The 50-char query limit means at most 49 `.*?` quantifiers
- In practice, the regex engine handles this within milliseconds
- The amplification factor (N items in index) is the bigger concern, but with bounded per-call time, total time remains acceptable

If further hardening is desired in the future, the regex-based approach could be replaced entirely with a linear-time iterative subsequence matcher. However, this is outside the scope of SEC-07.

#### Task 4.3.3: Confirm no bypass paths exist
Verify there is no way to call `matchSubsequence()` without going through the guards:
- The function is exported and could be called by future code, but the guards are inside the function itself, not in callers
- All current callers (`searchIndex.ts`, `searchHighlight.ts`) pass through the same function
- The guards cannot be bypassed by any current code path
