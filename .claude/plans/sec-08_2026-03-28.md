# SEC-08: Fix SSRF Risk in verifyImageUrl with redirect:follow

**Date:** 2026-03-28
**Severity:** Medium | **OWASP:** CWE-918 (SSRF)
**Affected file:** `backend/verifyImagePaths.ts` (lines 233-282)

---

## Problem Statement

The `verifyImageUrl()` function makes HTTP requests to URLs that are constructed from database-sourced path segments combined with a configured `baseUrl`. These requests use `redirect: 'follow'`, which means the Node.js `fetch()` implementation will automatically follow HTTP redirects without any validation of the redirect destination.

```typescript
// backend/verifyImagePaths.ts:250
let res = await fetch(url, { method: 'HEAD', redirect: 'follow', signal: controller.signal });
```

And again on the GET fallback path (line 256):
```typescript
res = await fetch(url, { method: 'GET', redirect: 'follow', signal: controller.signal });
```

### SSRF Attack Vectors

There are two distinct attack vectors:

1. **Redirect-based SSRF:** A legitimate-looking initial URL (e.g., `https://cdn.example.com/images/album1/photo.jpg`) could return a 3xx redirect to an internal resource (`http://169.254.169.254/latest/meta-data/`, `http://127.0.0.1:8080/admin`, `http://10.0.0.1/internal`). With `redirect: 'follow'`, Node.js fetch silently follows this redirect and returns the internal resource's response.

2. **Direct URL construction:** The `buildImageUrl()` function concatenates `baseUrl` with a `pathSegment` from database data. While the `baseUrl` comes from `image-config.json` (admin-controlled), the path segments originate from the Gallery 2 MySQL database. If the database were compromised, path segments could theoretically be crafted to produce URLs targeting internal services when combined with certain base URL configurations.

### Data Flow

```
image-config.json (baseUrl) + data/*.json (pathSegments from MySQL)
    |
    v
buildImageUrl(baseUrl, pathSegment)  -->  "https://cdn.example.com/albums/path.jpg"
    |
    v
collectImageUrlsFromAlbumTree()  -->  UrlToVerify[]
    |
    v
verifyUrls() -> verifyImageUrl()  -->  fetch(url, { redirect: 'follow' })
    |
    v
HTTP request follows redirects without destination validation
```

### Risk Assessment

The backend is a local admin tool (not internet-facing), which limits the practical impact. However:
- The tool runs on the admin's machine, which may have access to cloud metadata endpoints (169.254.169.254), internal services, and private network resources
- It processes data from a MySQL database that may have been populated by untrusted users (Gallery 2 allowed user uploads and metadata)
- The `redirect: 'follow'` behavior means even URLs that initially appear safe can reach internal targets

### Current Protections (None)

- No URL hostname validation before fetch
- No protocol validation (only `url.startsWith('http')` check on line 241, which allows both `http:` and `https:` but also `httpevil://...`)
- No redirect destination validation
- No IP address range blocking
- No DNS rebinding protection

### Section 1.2: Define the Validation Strategy

#### Task 1.2.1: Define private/reserved IP ranges to block
The `isPublicUrl()` helper must block requests to:

| Range | Description |
|-------|-------------|
| `127.0.0.0/8` | Loopback (localhost) |
| `10.0.0.0/8` | Private (RFC 1918) |
| `172.16.0.0/12` | Private (RFC 1918): 172.16.0.0 - 172.31.255.255 |
| `192.168.0.0/16` | Private (RFC 1918) |
| `169.254.0.0/16` | Link-local / cloud metadata (AWS, GCP, Azure) |
| `0.0.0.0/8` | "This network" |
| `::1` | IPv6 loopback |
| `fc00::/7` | IPv6 unique local (fd00::/8 and fc00::/8) |
| `fe80::/10` | IPv6 link-local |
| `::ffff:127.0.0.1` etc. | IPv4-mapped IPv6 addresses (must also check the mapped IPv4) |
| `localhost` | Hostname resolution to loopback |

Additionally, only `http:` and `https:` protocols should be allowed (block `file:`, `ftp:`, `data:`, `gopher:`, etc.).

#### Task 1.2.2: Decide on redirect handling strategy
Two options:

**Option A: Switch to `redirect: 'manual'` and validate redirect destinations.**
- Pros: Catches redirect-based SSRF completely
- Cons: Must manually follow redirects (loop with limit), more code, must handle relative redirect URLs

**Option B: Validate initial URL only, keep `redirect: 'follow'`.**
- Pros: Simpler, minimal code change
- Cons: Does not catch redirect-based SSRF (a public URL that redirects to a private IP)

**Decision: Option A.** Redirect-based SSRF is the primary attack vector described in the issue. Simply validating the initial URL is insufficient since the vulnerability is specifically about `redirect: 'follow'` allowing redirects to internal targets.

However, given that this is a local admin tool with limited attack surface, a pragmatic middle ground is acceptable: validate the initial URL before the first fetch, then switch to `redirect: 'manual'` and validate each redirect destination before following it, with a reasonable redirect limit (e.g., 10).

#### Task 1.2.3: Decide placement of the validation helper
The `isPublicUrl()` function should be:
- Defined in `backend/verifyImagePaths.ts` as a non-exported helper (internal to the module)
- Placed above `verifyImageUrl()` alongside the other helpers
- Not exported -- it is specific to this module's SSRF protection concern

#### Task 2.1.1: Add `isPrivateHostname()` helper function
Add a private helper that checks whether a hostname resolves to or represents a private/reserved IP address.

```typescript
/**
 * Check whether an IPv4 address string falls within private or reserved ranges.
 * Handles dotted-decimal format only (e.g., "192.168.1.1").
 */
function isPrivateIPv4(ip: string): boolean {
  const parts = ip.split('.').map(Number);
  if (parts.length !== 4 || parts.some((p) => isNaN(p) || p < 0 || p > 255)) {
    return false; // not a valid IPv4 -- let caller decide
  }
  const [a, b] = parts;
  return (
    a === 127 ||                        // 127.0.0.0/8 (loopback)
    a === 10 ||                         // 10.0.0.0/8 (private)
    (a === 172 && b >= 16 && b <= 31) || // 172.16.0.0/12 (private)
    (a === 192 && b === 168) ||          // 192.168.0.0/16 (private)
    (a === 169 && b === 254) ||          // 169.254.0.0/16 (link-local / cloud metadata)
    a === 0                             // 0.0.0.0/8 ("this network")
  );
}

/**
 * Check whether an IPv6 address is private/reserved (loopback, link-local,
 * unique local, or an IPv4-mapped address with a private IPv4).
 */
function isPrivateIPv6(ip: string): boolean {
  const lower = ip.toLowerCase();
  // IPv6 loopback
  if (lower === '::1' || lower === '0000:0000:0000:0000:0000:0000:0000:0001') {
    return true;
  }
  // IPv6 link-local (fe80::/10)
  if (lower.startsWith('fe80:') || lower.startsWith('fe80%')) {
    return true;
  }
  // IPv6 unique local (fc00::/7 covers fc00:: and fd00::)
  if (lower.startsWith('fc') || lower.startsWith('fd')) {
    return true;
  }
  // IPv4-mapped IPv6 (::ffff:x.x.x.x)
  const v4MappedMatch = lower.match(/^::ffff:(\d+\.\d+\.\d+\.\d+)$/);
  if (v4MappedMatch) {
    return isPrivateIPv4(v4MappedMatch[1]);
  }
  return false;
}

/**
 * Validate that a URL targets a public host using only http: or https: protocol.
 * Returns { valid: true } if the URL is safe to fetch, or { valid: false, reason }
 * if it should be blocked.
 */
function validatePublicUrl(urlString: string): { valid: true } | { valid: false; reason: string } {
  let parsed: URL;
  try {
    parsed = new URL(urlString);
  } catch {
    return { valid: false, reason: 'Malformed URL' };
  }

  // Protocol check
  if (parsed.protocol !== 'http:' && parsed.protocol !== 'https:') {
    return { valid: false, reason: `Disallowed protocol: ${parsed.protocol}` };
  }

  const hostname = parsed.hostname.toLowerCase();

  // Block 'localhost' and common aliases
  if (
    hostname === 'localhost' ||
    hostname === 'localhost.' ||
    hostname.endsWith('.localhost') ||
    hostname.endsWith('.localhost.')
  ) {
    return { valid: false, reason: 'Localhost is not allowed' };
  }

  // Strip IPv6 brackets for address checking
  const bareHost = hostname.startsWith('[') && hostname.endsWith(']')
    ? hostname.slice(1, -1)
    : hostname;

  // Check IPv4
  if (/^\d+\.\d+\.\d+\.\d+$/.test(bareHost)) {
    if (isPrivateIPv4(bareHost)) {
      return { valid: false, reason: `Private IPv4 address: ${bareHost}` };
    }
  }

  // Check IPv6
  if (bareHost.includes(':')) {
    if (isPrivateIPv6(bareHost)) {
      return { valid: false, reason: `Private IPv6 address: ${bareHost}` };
    }
  }

  return { valid: true };
}
```

#### Task 2.2.3: Add redirect-following loop with validation
Replace the current simple fetch logic with a loop that:
1. Makes the request with `redirect: 'manual'`
2. If the response is a 3xx redirect, extracts the `Location` header
3. Validates the redirect destination with `validatePublicUrl()`
4. Follows the redirect up to a configurable limit (default: 10)
5. If the redirect target fails validation, returns an error

The full rewrite of `verifyImageUrl()`:

```typescript
const MAX_REDIRECTS = 10;

export async function verifyImageUrl(
    url: string,
    timeoutMs: number = DEFAULT_TIMEOUT_MS,
    projectRoot?: string,
): Promise<{ ok: boolean; status?: number; error?: string }> {
    if (!url) {
        return { ok: false, error: 'Empty URL' };
    }
    if (!url.startsWith('http')) {
        if (projectRoot) {
            return verifyLocalFile(url, projectRoot);
        }
        return { ok: false, error: 'URL not HTTP(S) and no projectRoot for local check' };
    }

    // Validate initial URL against SSRF
    const initialCheck = validatePublicUrl(url);
    if (!initialCheck.valid) {
        return { ok: false, error: `Blocked: ${initialCheck.reason}` };
    }

    let currentUrl = url;
    let method: 'HEAD' | 'GET' = 'HEAD';
    let redirectCount = 0;

    while (redirectCount <= MAX_REDIRECTS) {
        const controller = new AbortController();
        const timeoutId = setTimeout(() => controller.abort(), timeoutMs);
        try {
            const res = await fetch(currentUrl, {
                method,
                redirect: 'manual',
                signal: controller.signal,
            });
            clearTimeout(timeoutId);

            // Handle 405 Method Not Allowed: retry with GET
            if (res.status === 405 && method === 'HEAD') {
                method = 'GET';
                continue; // retry same URL with GET, does not count as redirect
            }

            // Handle redirects
            if (res.status >= 300 && res.status < 400) {
                const location = res.headers.get('Location');
                if (!location) {
                    return { ok: false, status: res.status, error: `Redirect ${res.status} with no Location header` };
                }

                // Resolve relative redirect URLs against current URL
                let redirectUrl: string;
                try {
                    redirectUrl = new URL(location, currentUrl).href;
                } catch {
                    return { ok: false, status: res.status, error: `Redirect to invalid URL: ${location}` };
                }

                // Validate redirect destination against SSRF
                const redirectCheck = validatePublicUrl(redirectUrl);
                if (!redirectCheck.valid) {
                    return { ok: false, status: res.status, error: `Redirect blocked: ${redirectCheck.reason}` };
                }

                // Discard response body before following redirect
                if (res.body) {
                    await res.body.cancel().catch(() => {});
                }

                currentUrl = redirectUrl;
                redirectCount++;
                continue;
            }

            // Non-redirect response: check status and content type
            if (!res.ok) {
                const err = res.status === 404 ? '404 Not Found'
                    : res.status >= 500 ? `${res.status} server error`
                    : `${res.status}`;
                return { ok: false, status: res.status, error: err };
            }

            const contentType = res.headers.get('Content-Type');
            if (!isImageContentType(contentType)) {
                return { ok: false, status: res.status, error: `not an image (Content-Type: ${contentType ?? 'missing'})` };
            }

            if (res.body) {
                await res.body.cancel().catch(() => {});
            }
            return { ok: true, status: res.status };
        } catch (err) {
            clearTimeout(timeoutId);
            const isTimeout = err instanceof Error && err.name === 'AbortError';
            return { ok: false, error: isTimeout ? `timeout after ${timeoutMs}ms` : (err instanceof Error ? err.message : String(err)) };
        }
    }

    return { ok: false, error: `Too many redirects (>${MAX_REDIRECTS})` };
}
```

Key changes from the original:
- `redirect: 'manual'` instead of `redirect: 'follow'`
- `validatePublicUrl()` called on initial URL and every redirect target
- Manual redirect loop with configurable limit (MAX_REDIRECTS = 10)
- Relative redirect URLs resolved via `new URL(location, currentUrl)`
- 405 retry preserved but refactored into the loop (does not count as a redirect)
- Response body discarded before following each redirect

### Section 4.3: Edge Case Review

#### Task 4.3.1: DNS rebinding consideration
Note that `validatePublicUrl()` validates the URL hostname at parse time, not at DNS resolution time. A DNS rebinding attack (where a hostname resolves to a public IP on first lookup, then to a private IP on subsequent lookups) is NOT prevented by this implementation.

Full DNS rebinding protection would require resolving the hostname to an IP address and validating the IP before connecting. This is non-trivial with Node.js `fetch()` and would require a custom DNS resolver or a connect callback.

**Decision:** Document this limitation as a known gap. The risk is low for a local admin tool, and DNS rebinding requires an attacker-controlled DNS server plus the ability to inject hostnames into the image-config.json baseUrl (which is admin-controlled).

#### Task 4.3.2: Decimal/octal IP representation
Some URL parsers accept IPs in decimal (`http://2130706433` for 127.0.0.1) or octal (`http://0177.0.0.1` for 127.0.0.1) notation. The `URL` constructor in Node.js normalizes these to dotted-decimal in the `hostname` property, so `new URL('http://2130706433').hostname` returns `'127.0.0.1'`. Verify this is the case with Node.js's URL parser.

If `URL` does NOT normalize these, add handling for decimal and octal IP representations. If it does normalize them, no additional handling is needed.
