# SEC-10: Fix BBCode Parser Direct Style Property Injection

**Date:** 2026-03-28
**Severity:** Medium | **OWASP:** CWE-79 (XSS)
**Affected files:**
- `frontend/src/utils/bbcode.ts` (lines 185-201, 435-441)
- `frontend/src/utils/bbcode.test.ts`

---

## Problem Statement

The BBCode parser injects user-supplied color and size values directly into React style objects at lines 437-439:

```typescript
if (tagMatch.attributes.color) {
  props.style = { color: tagMatch.attributes.color };
} else if (tagMatch.attributes.size) {
  props.style = { fontSize: tagMatch.attributes.size };
}
```

These values pass through `sanitizeStyleValue()` (lines 185-201), which delegates to the `validateAttribute` functions defined in `TAG_CONFIGS` (lines 84-139). The existing validators are already quite robust:

- **Color validator** (lines 84-114): Accepts only `#rgb`/`#rrggbb` hex patterns, strict `rgb(r,g,b)` / `rgba(r,g,b,a)` with range-checked numeric values, and a fixed allowlist of 16 named colors.
- **Size validator** (lines 126-129): Accepts only integers 1-72 via `parseInt()`, then the transformer appends `px`.

However, neither `sanitizeStyleValue()` nor the validators explicitly reject CSS injection keywords that could be dangerous in older or non-standard browsers:

1. **`expression()`** - Executes JavaScript in IE6-IE9 (e.g., `expression(alert(1))` as a CSS value).
2. **`url(javascript:...)`** - Some older browsers evaluate JavaScript in CSS `url()` values.
3. **`@import`** - Can load external stylesheets in CSS contexts.
4. **`url(data:...)`** - Can embed content via data URIs in CSS.

While the current allowlist-based validators already make it very difficult to smuggle these payloads through (none of the patterns above match the hex, rgb, rgba, or named-color formats), a defense-in-depth approach adds an explicit blocklist check in `sanitizeStyleValue()`. This protects against:
- Future modifications to the validators that might relax the allowlist
- Edge cases where a value somehow passes validation but contains dangerous substrings
- Browser-specific CSS parsing quirks that might interpret values differently

### Data Flow

```
BBCode input string
  -> parseBBCodeInternal() parses [color=VALUE] or [size=VALUE]
    -> parseTag() -> parseAttribute() -> sanitizeStyleValue()
      -> TAG_CONFIGS.color.validateAttribute(VALUE)  [allowlist check]
      -> TAG_CONFIGS.color.transformAttribute(VALUE)  [trim/format]
    -> returned value set on React style object: { color: VALUE }
      -> React renders as inline style on <span>
```

The fix adds a blocklist check at the `sanitizeStyleValue()` level, before the value reaches the React style object, as a second layer behind the existing allowlist validators.

#### Task 1.1.1: Trace the color value flow end-to-end

#### Task 1.1.2: Verify the color validator rejects known attack patterns
Test mentally (and confirm via tests later) that the existing allowlist rejects:
- `expression(alert(1))` - Not a hex, rgb, rgba, or named color. **Rejected.**
- `url(javascript:alert(1))` - Not a hex, rgb, rgba, or named color. **Rejected.**
- `red; expression(alert(1))` - Contains semicolon, fails all patterns. **Rejected.**
- `red\nexpr` - Contains whitespace/newline, fails strict patterns. **Rejected.**

Confirm that the current validators are already effective but lack explicit keyword blocking.

#### Task 1.1.3: Verify the size validator rejects known attack patterns
Test mentally that `parseInt(value, 10)` plus the range check 1-72 rejects:
- `expression(alert(1))` - `parseInt()` returns `NaN`. **Rejected.**
- `12; expression(alert(1))` - `parseInt()` returns `12` (stops at semicolon), passes range check. But `transformAttribute` outputs `12px`, discarding the payload. **Safe but accidental.**
- `url(javascript:...)` - `parseInt()` returns `NaN`. **Rejected.**

Note that the size transformer's `parseInt` + template literal approach coincidentally sanitizes payloads by extracting only the number. Document this as an observation but still add the defense-in-depth check.

#### Task 1.1.4: Assess the parseAttribute bare-value path
At lines 219-226, when `equalIndex === -1` (bare attribute like `[color red]`), the value goes through `sanitizeStyleValue()` the same way. Confirm this path also benefits from the fix.

### Section 1.2: Define the Blocklist

#### Task 1.2.1: Identify dangerous CSS keywords to block
The following case-insensitive keywords should be rejected if found anywhere in a style value:

| Keyword | Attack Vector | Affected Browsers |
|---------|--------------|-------------------|
| `expression` | `expression(alert(1))` executes JS | IE6-IE9 |
| `url(` | `url(javascript:...)` executes JS | Older IE, some WebKit |
| `javascript:` | Protocol handler in CSS url() | Older browsers |
| `import` | `@import` loads external CSS | All browsers (in stylesheet context) |

#### Task 1.2.2: Decide on blocklist implementation approach
The blocklist check should:
1. Be case-insensitive (attackers use mixed case: `eXpReSsIoN()`)
2. Check the lowercased value against literal substrings (no regex needed)
3. Return `null` (rejection) if any keyword is found
4. Run **inside** `sanitizeStyleValue()`, after the existing validation passes, as a final gate

This ensures the blocklist acts as defense-in-depth behind the allowlist, not as a replacement for it.

## Phase 2: Implementation

### Section 2.1: Add the Blocklist Check to sanitizeStyleValue

#### Task 2.1.1: Add the UNSAFE_STYLE_KEYWORDS constant
Add a constant array immediately above `sanitizeStyleValue()` (before line 185):

```typescript
/**
 * CSS keywords that could enable script execution in older browsers.
 * Checked as a defense-in-depth measure behind the existing allowlist
 * validators in TAG_CONFIGS.
 */
const UNSAFE_STYLE_KEYWORDS = ["expression", "url(", "javascript:", "import"];
```

Location: Place at module level, after the `URL_SCHEME_REGEX` constant (line 155) and before `clearBBCodeCache()` (line 160), or directly above `sanitizeStyleValue()`.

#### Task 2.1.2: Add the containsUnsafeKeyword helper function
Add a private helper function immediately after the constant:

```typescript
/**
 * Check if a CSS value contains any unsafe keywords that could enable
 * script execution in older browsers (expression(), url(javascript:), etc.).
 * Case-insensitive check as a defense-in-depth layer.
 */
function containsUnsafeStyleKeyword(value: string): boolean {
  const lower = value.toLowerCase();
  return UNSAFE_STYLE_KEYWORDS.some((keyword) => lower.includes(keyword));
}
```

This is a separate function (not inline) for testability and clarity. It is not exported -- it is an internal helper.

#### Task 2.1.3: Add the blocklist check to sanitizeStyleValue for color
Modify the color branch in `sanitizeStyleValue()` to add the blocklist check after validation passes but before returning the value.

Before (lines 186-191):
```typescript
if (property === 'color') {
  const config = TAG_CONFIGS.color;
  if (config.validateAttribute && !config.validateAttribute(value)) {
    return null; // Invalid color value
  }
  return config.transformAttribute ? config.transformAttribute(value) : value;
}
```

After:
```typescript
if (property === 'color') {
  const config = TAG_CONFIGS.color;
  if (config.validateAttribute && !config.validateAttribute(value)) {
    return null; // Invalid color value
  }
  const transformed = config.transformAttribute
    ? config.transformAttribute(value)
    : value;
  if (containsUnsafeStyleKeyword(transformed)) {
    return null; // Defense-in-depth: reject dangerous CSS keywords
  }
  return transformed;
}
```

Key change: The blocklist check runs on the **transformed** value (post-trim), not the raw input. This ensures no keyword is introduced by the transformer (though the current color transformer only trims).

#### Task 2.1.4: Add the blocklist check to sanitizeStyleValue for font-size
Apply the same pattern to the font-size branch.

Before (lines 193-199):
```typescript
if (property === 'font-size') {
  const config = TAG_CONFIGS.size;
  if (config.validateAttribute && !config.validateAttribute(value)) {
    return null; // Invalid size value
  }
  return config.transformAttribute ? config.transformAttribute(value) : value;
}
```

After:
```typescript
if (property === 'font-size') {
  const config = TAG_CONFIGS.size;
  if (config.validateAttribute && !config.validateAttribute(value)) {
    return null; // Invalid size value
  }
  const transformed = config.transformAttribute
    ? config.transformAttribute(value)
    : value;
  if (containsUnsafeStyleKeyword(transformed)) {
    return null; // Defense-in-depth: reject dangerous CSS keywords
  }
  return transformed;
}
```

Note: For size, the transformer outputs `${numValue}px` which can never contain unsafe keywords. The check is still added for consistency and to guard against future transformer changes.

Add a new `describe` block in `frontend/src/utils/bbcode.test.ts` inside the existing `parseBBCode` describe, after the "Security - XSS prevention" block:

```typescript
describe("SEC-10: Defense-in-depth style injection prevention", () => {
  it("rejects expression() in color value", () => {
    const result = parseBBCode(
      "[color=expression(alert(1))]Text[/color]"
    );

      "[color=url(javascript:alert(1))]Text[/color]"

    expect(container.textContent).toContain("Text");
  });

  it("rejects javascript: in color value", () => {

      "[color=javascript:alert(1)]Text[/color]"

      "[color=import]Text[/color]"

    const { container } = render(<>{result}</>);
    expect(container.querySelector("span")).not.toBeInTheDocument();

      "[size=expression(alert(1))]Text[/size]"

    const { container } = render(<>{result}</>);
```

## Phase 5: End-to-End Review

### Section 5.1: Full Tracing

#### Task 5.1.1: Trace a malicious color value end-to-end (post-fix)
Input: `[color=expression(alert(1))]Evil[/color]`

1. `parseBBCodeInternal()` finds `[color=expression(alert(1))]`
2. `parseTag()` extracts tagName `color`, attrString `expression(alert(1))`
3. `parseAttribute()` sees no `=` in attrString, routes to bare-value path (line 219)
4. `sanitizeStyleValue('color', 'expression(alert(1))')` called
5. **Layer 1:** `TAG_CONFIGS.color.validateAttribute('expression(alert(1))')` called
   - Not hex (`/^#...$/` fails)
   - Not rgb (`/^rgb\(...\)$/` fails)
   - Not rgba (`/^rgba\(...\)$/` fails)
   - Not in namedColors array
   - Returns `false` -> `sanitizeStyleValue` returns `null`
6. `parseAttribute()` returns `null` at line 227
7. `parseTag()` returns `{ name: 'color', isClosing: false, attributes: null }`
8. Back in `parseBBCodeInternal()`: `tagMatch.attributes` is null, so no attributes set
9. Since color tag has no valid attributes, the tag content is rendered but the `<span>` has no style prop

**Result:** Attack blocked by Layer 1 (allowlist). Layer 2 (blocklist) would also catch it if Layer 1 were bypassed.

#### Task 5.1.2: Trace a hypothetical validator bypass (post-fix)
Hypothetical scenario: Future code change adds a named color that happens to contain a dangerous keyword, or the rgb regex is relaxed.

If somehow `validateAttribute` returns `true` for `expression(alert(1))`:
1. `sanitizeStyleValue` proceeds to transform: `transformAttribute('expression(alert(1))')` returns `'expression(alert(1))'` (just trimmed)
2. **Layer 2:** `containsUnsafeStyleKeyword('expression(alert(1))')` called
3. `'expression(alert(1))'.toLowerCase()` = `'expression(alert(1))'`
4. `'expression(alert(1))'.includes('expression')` = `true`
5. Returns `true` -> `sanitizeStyleValue` returns `null`

**Result:** Attack blocked by Layer 2 (blocklist), even if Layer 1 is bypassed.

#### Task 5.1.3: Trace a valid color value end-to-end (post-fix)
Input: `[color=red]Hello[/color]`

1. `parseBBCodeInternal()` finds `[color=red]`
2. `parseTag()` extracts tagName `color`, attrString `red`
3. `parseAttribute()` routes to bare-value path
4. `sanitizeStyleValue('color', 'red')` called
5. **Layer 1:** `validateAttribute('red')` - in namedColors array -> returns `true`
6. Transform: `transformAttribute('red')` returns `'red'` (just trimmed)
7. **Layer 2:** `containsUnsafeStyleKeyword('red')` - `'red'` does not contain any keyword -> returns `false`
8. `sanitizeStyleValue` returns `'red'`
9. `parseAttribute` returns `{ color: 'red' }`
10. At line 437: `props.style = { color: 'red' }`
11. React renders `<span style="color: red;">Hello</span>`

**Result:** Valid value passes both layers correctly.
