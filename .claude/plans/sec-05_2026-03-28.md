# SEC-05: Fix Path Traversal in generateThumbnail.ts via Database-Sourced Paths

**Date:** 2026-03-28
**Severity:** High | **OWASP:** CWE-22 (Path Traversal)
**Affected files:**
- `backend/generateThumbnail.ts` (lines 27-60)
- `backend/generateThumbnail.test.ts`
- `backend/index.ts` (lines 346-372, call site)

---

## Problem Statement

`generateThumbnail()` accepts `sourcePath` and `destPath` as arbitrary strings and performs filesystem operations on them without validating that they remain within expected base directories. The function:

1. **Calls `fs.access(destPath)`** to check if the destination exists -- probes arbitrary filesystem locations.
2. **Calls `fs.access(sourcePath)`** to check if the source exists -- probes arbitrary filesystem locations.
3. **Calls `fs.mkdir(destDir, { recursive: true })`** which can create directories anywhere on the filesystem.
4. **Reads `sourcePath` via `sharp(sourcePath)`** -- reads arbitrary files.
5. **Writes to `destPath` via `.toFile(destPath)`** -- writes to arbitrary locations.

If the Gallery 2 MySQL database is compromised (e.g., SQL injection in another tool, direct DB access by an attacker, or a malicious database dump), a crafted `pathComponent` value like `../../etc/cron.d/backdoor` would produce paths that escape the intended directories.

### Data Flow

The paths are constructed in `backend/index.ts:349-350`:
```typescript
const sourcePath = path.join(albumsRoot, fullPath);
const destPath = path.join(thumbnailsRoot, highlightThumbnailUrlPath);
```

Where:
- `albumsRoot` = config value, typically `frontend/public/g2data/albums` (resolved relative to project root)
- `thumbnailsRoot` = config value, typically `frontend/public/g2data/thumbnails`
- `fullPath` = database-sourced `pathComponent` values joined with `/`
- `highlightThumbnailUrlPath` = derived from `pathComponent` chain via `buildPathsFromPathComponent()`

Note: `buildPathsFromPathComponent()` in `pathResolution.ts` already validates individual components for `..`, `/`, `\`, and null bytes. However, `generateThumbnail()` should perform its own defense-in-depth validation since it is the function that performs the actual filesystem operations and cannot assume its callers always pre-validate.

### Existing Working Copy Issue

The working copy already contains a `validatePathWithinBase()` function, but the implementation is flawed. It validates each path against its own `path.dirname()`:
```typescript
const sourceBase = path.dirname(path.resolve(sourcePath));
validatePathWithinBase(sourcePath, sourceBase);
```
This is circular -- any file trivially resides within its own parent directory. The validation must check against the **expected base directory** (`albumsRoot` / `thumbnailsRoot`), not the path's own parent.

### Security Context

Per CLAUDE.md: "The backend is a one-shot admin tool, not a running server. Security concerns about the backend code are low-impact since it runs locally by a trusted admin." The threat model is a compromised database producing malicious path values, not a remote attacker calling the function directly. Defense-in-depth is still warranted to prevent data corruption or unintended filesystem modifications during extraction.

## Phase 1: Research & Impact Analysis

### Section 1.1: Understand Current Behavior

#### Task 1.1.1: Trace the full data flow from database to filesystem
Confirm the path construction chain:
1. `sql.getChildren(root)` returns `Child[]` with `pathComponent` from the database
2. `index.ts:341` builds `pathComponentChain` by concatenating ancestor components + child component
3. `index.ts:342` joins the chain: `fullPath = pathComponentChain.join('/')`
4. `index.ts:344` calls `buildPathsFromPathComponent()` which validates individual components and builds `highlightThumbnailUrlPath`
5. `index.ts:349` constructs `sourcePath = path.join(albumsRoot, fullPath)`
6. `index.ts:350` constructs `destPath = path.join(thumbnailsRoot, highlightThumbnailUrlPath)`
7. `index.ts:354` passes both to `generateThumbnail(sourcePath, destPath, ...)`

Verify that `albumsRoot` and `thumbnailsRoot` are known at the call site and could be passed to the validation.

#### Task 1.1.2: Assess pathResolution.ts pre-validation
`buildPathsFromPathComponent()` in `pathResolution.ts:19-33` already validates:
- No `..` in any component
- No `/` in any component
- No `\` in any component
- No null bytes in any component

This covers the most common traversal vectors at the component level. However:
- `fullPath` is built separately from `pathComponentChain.join('/')` in `index.ts:342`, not via `buildPathsFromPathComponent()`
- `generateThumbnail()` is a public exported function that other callers might use without the `pathResolution.ts` pre-check
- Defense-in-depth: filesystem-modifying functions should validate their own inputs

#### Task 1.1.3: Analyze the `path.join()` behavior with traversal
Confirm that `path.join('/base/dir', '../../etc/passwd')` resolves to `/etc/passwd` -- i.e., `path.join` does NOT prevent traversal. This is the core vulnerability: even though individual components are validated by `pathResolution.ts`, the concatenated `fullPath` in `index.ts:342` is not re-validated before reaching `generateThumbnail()`.

#### Task 1.1.4: Review the flawed existing implementation
The working copy's `validatePathWithinBase()` calls are:
```typescript
const sourceBase = path.dirname(path.resolve(sourcePath));
validatePathWithinBase(sourcePath, sourceBase);
```
This always passes because any path is within its own dirname. The fix requires passing the actual expected base directories (`albumsRoot`, `thumbnailsRoot`) from the caller.

### Section 1.2: Design the Fix

#### Task 1.2.1: Decide the function signature approach
Two options:

**Option A: Add base directory parameters to `generateThumbnail()`**
```typescript
export async function generateThumbnail(
    sourcePath: string,
    destPath: string,
    sourceBaseDir: string,
    destBaseDir: string,
    options?: Partial<ThumbnailOptions>,
): Promise<...>
```
Pro: Self-contained, validates in the same function that does I/O.
Con: Changes the public API. Callers must supply base directories.

**Option B: Keep the `validatePathWithinBase()` helper exportable and call it at the call site in `index.ts`**
Pro: No signature change to `generateThumbnail()`.
Con: Validation is separated from the I/O, which defeats defense-in-depth.

Decision: **Option A.** The function that performs filesystem operations should know and enforce its boundaries. Changing the signature is acceptable because:
- There is only one call site (`index.ts:354`)
- The backend is a one-shot script, not a library with external consumers
- This makes `generateThumbnail()` safe by default regardless of caller

#### Task 1.2.2: Define the validation logic
The `validatePathWithinBase()` helper should:
1. Reject paths containing null bytes (`\0`)
2. Resolve both the file path and the base directory to absolute paths via `path.resolve()`
3. Verify the resolved file path starts with `resolvedBase + path.sep` (or equals `resolvedBase`)
4. Throw an `Error` with a descriptive message on failure

This approach is more robust than checking for `..` substrings because:
- `path.resolve()` normalizes all forms of relative references
- It catches edge cases like `path.join('/base', 'a/../../escape')` which resolves to `/escape`
- It is not dependent on the path separator format

Note: We do NOT use `fs.realpath()` here because the source/dest paths may not exist yet (the dest file is about to be created). `path.resolve()` operates purely on path strings and does not require the path to exist. Symlink resolution is out of scope for this fix (SEC-06 covers the symlink case in `verifyImagePaths.ts`).

#### Task 1.2.3: Decide error handling behavior
When validation fails, the function should throw an `Error` (not return a status string). Rationale:
- Path traversal is a security violation, not an expected condition like "missing" or "invalid"
- The caller in `index.ts:366-369` already has a `catch` block that handles thrown errors by logging a warning and incrementing `excludedCount`
- Throwing makes the failure visible and prevents silent continuation

## Phase 2: Implementation

### Section 2.1: Update the `validatePathWithinBase()` Helper

#### Task 2.1.1: Fix the `validatePathWithinBase()` function
Replace the existing (flawed) implementation in `backend/generateThumbnail.ts`. The corrected function:

```typescript
/**
 * Validate that a file path resolves to a location within a base directory.
 * Prevents path traversal attacks from database-sourced path values.
 *
 * Uses path.resolve() (not fs.realpath()) so it works for paths that
 * don't yet exist on disk (e.g., destination files about to be created).
 *
 * @param filePath - The file path to validate
 * @param baseDir - The base directory the path must reside within
 * @throws Error if the path escapes the base directory or contains null bytes
 */
export function validatePathWithinBase(filePath: string, baseDir: string): void {
    if (filePath.includes('\0')) {
        throw new Error(`Path contains null byte: ${filePath.replace(/\0/g, '\\0')}`);
    }

    const resolvedPath = path.resolve(filePath);
    const resolvedBase = path.resolve(baseDir);

    if (!resolvedPath.startsWith(resolvedBase + path.sep) && resolvedPath !== resolvedBase) {
        throw new Error(`Path escapes base directory: ${resolvedPath} is not within ${resolvedBase}`);
    }
}
```

Key changes from the working copy:
- Return type changed from `boolean` to `void` (it throws on failure; returning `true` was misleading and unused)
- JSDoc updated to explain why `path.resolve()` is used instead of `fs.realpath()`
- Logic is identical to the working copy helper body, but the call sites will be fixed

#### Task 2.1.2: Update `generateThumbnail()` signature and validation calls
Change the function signature to accept base directory parameters:

```typescript
export async function generateThumbnail(
    sourcePath: string,
    destPath: string,
    sourceBaseDir: string,
    destBaseDir: string,
    options: Partial<ThumbnailOptions> = {},
): Promise<'generated' | 'skipped' | 'missing' | 'invalid'> {
    const opts = { ...DEFAULT_OPTIONS, ...options };

    // Validate paths are within expected base directories
    validatePathWithinBase(sourcePath, sourceBaseDir);
    validatePathWithinBase(destPath, destBaseDir);

    // ... rest of function unchanged
```

Remove the old circular validation calls:


## Phase 4: Code Review

### Section 4.1: Verify Implementation Correctness

#### Task 4.1.1: Confirm `validatePathWithinBase` handles edge cases
Walk through these inputs:

| Input | Expected |
|-------|----------|
| `validatePathWithinBase('/base/dir/file.jpg', '/base/dir')` | passes (within base) |
| `validatePathWithinBase('/base/dir', '/base/dir')` | passes (equals base) |
| `validatePathWithinBase('/base/dir/../escape', '/base/dir')` | throws (resolves to `/base/escape`) |
| `validatePathWithinBase('/base/directory/file', '/base/dir')` | throws (prefix match without separator would be wrong; `startsWith('/base/dir/')` correctly rejects `/base/directory/`) |
| `validatePathWithinBase('/base/dir/file\0.jpg', '/base/dir')` | throws (null byte) |
| `validatePathWithinBase('relative/path', '/base/dir')` | depends on cwd; `path.resolve('relative/path')` must start with `/base/dir/` |

The critical edge case is the **prefix boundary check**: `/base/directory` should NOT be treated as within `/base/dir`. The expression `resolvedPath.startsWith(resolvedBase + path.sep)` correctly handles this by requiring the path separator after the base.

### Section 4.2: Defense-in-Depth Assessment

#### Task 4.2.1: Verify layered protection
After this fix, path traversal is blocked at two layers:
1. **`pathResolution.ts:19-33`** (component-level): Rejects individual `pathComponent` values containing `..`, `/`, `\`, or null bytes before they are joined into paths.
2. **`generateThumbnail.ts:validatePathWithinBase()`** (resolved-path level): Validates the final resolved absolute paths are within the expected base directories before any filesystem operations.

This provides defense-in-depth: even if layer 1 is bypassed (e.g., a new code path that skips `buildPathsFromPathComponent()`), layer 2 prevents filesystem escape.

#### Task 4.2.2: Confirm `path.resolve()` is sufficient (no `fs.realpath()` needed)
`fs.realpath()` resolves symlinks, which `path.resolve()` does not. However:
- The destination file does not exist yet (it's about to be created), so `fs.realpath()` would fail
- Symlink attacks are a separate concern (SEC-06 covers this for `verifyImagePaths.ts`)
- The base directories (`albumsRoot`, `thumbnailsRoot`) are from the config file, which is trusted (written by the admin)
- For this threat model (compromised database values), `path.resolve()` is sufficient
